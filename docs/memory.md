# Память и контекст

Контекст оркестратора намеренно мал. Всё, что не помещается в «последнюю пару», заменено четырьмя механизмами.

| Механизм | Кто пишет | Область | Как попадает в модель | Хранилище |
|---|---|---|---|---|
| **Rules** | пользователь (`/rules set`) | global (user) или local (session) | всегда, блок «MANDATORY RULES» (без ID) | Sled (`userdata`, `sessions/{sid}`) |
| **Facts** | модель (`remember_fact`) или пользователь (`/facts add`) | user, между сессиями | авто-RAG перед каждым вызовом + `search_fact` | LanceDB (`context`) |
| **Dialog map** | ядро, автоматически | session | всегда, system-сообщение в начале | вычисляется из истории |
| **History** | ядро | session | последняя пара + `read_history(index)` | Sled (`sessions/{sid}`) |
| **Notes** *(предложение)* | модель | session | всегда, короткий блок | см. [notes-design.md](notes-design.md) |

## Rules

`UserRule { id, text, is_global, created_at }`. Глобальные лежат в профиле пользователя, локальные — в таблице сессии.
`load_rules` склеивает оба набора. Локальные правила копируются при `clone` сессии.
Это *инструкции пользователя модели*: модель правила не создаёт и не меняет.

## Dialog map

`Session::dialog_map(max_chars, max_turns)` показывает последние `dialog_map_turns` (30) ходов в виде `[i] user -> assistant`;
каждая сторона обрезана до `dialog_map_chars` (160) символов (`strip_markdown` + схлопывание пробелов).
Более ранние ходы помечены как пропущенные и доступны через `read_history`.

Строки кэшируются в `Session` (читаются из Sled один раз за активацию сессии, затем `write_messages` дописывает новую строку;
`clear` сбрасывает кэш). Раньше каждая итерация читала из БД все пары.

## Facts: как работает RAG сейчас

`UserFact { id, text, search_text, created_at }` + вектор. Устаревший `search_text` оставлен для совместимости хранилища и равен `text`
(у старых фактов там расширенный английский вариант).

**Запись** (`UserState::save_fact(text, replaces, guard_similar)`):

1. Эмбеддинг считается по исходному тексту (`Search::Document`). Перевода и LLM-«нормализации» больше нет.
2. Поиск до 5 соседей выше `dedup_similarity` (по умолчанию 0.92, не ниже 0.85).
3. Точный дубликат (без учёта регистра и пробелов, Unicode) — ничего не меняется.
4. `replaces = Some(id)` — удаляется ровно этот факт.
5. Если `guard_similar` и соседи есть — **ничего не пишется**, модели возвращаются похожие факты с ID и подсказка:
   `replaces` (обновить) или `keep_both = true` (сохранить отдельно).
6. Иначе запись `(id, embedding, UserFact)`. Пользовательская команда `/facts add` пишет без проверки на похожие.

Автоматических удалений больше нет.

**Чтение** (`UserState::search_facts`):

1. `utils::fact_query`: без блоков кода и markdown, пробелы схлопнуты, не более 300 символов. Язык сохраняется.
2. Эмбеддинг `Search::Query`, затем гибридный поиск `cistern` (подробно в [cistern-search.md](cistern-search.md)):
   косинусная близость ≥ `fact_similarity` и не дальше `fact_margin` от лучшего хита, плюс точные совпадения слов (имена, версии, модели);
   ранги сливаются через RRF. Лимит — `search_limit` (×2 для явного запроса модели).

**Использование:**

- *Авто-RAG:* один раз на запрос пользователя, пропускается для реплик вроде «ок», «спасибо»; в промпт попадает блок `USER FACTS`
  (без ID), ограниченный `search_limit` и `facts_max_chars` (800).
- *Явный:* `search_fact{query, limit}`; в результате — факты с ID (нужны для `replaces`). Промпт просит вызывать его только если факта не хватает.

**Пороги** (`config.toml`, секция `context`) ограничиваются кодом: `fact_similarity` ∈ [0, 1] (по умолчанию 0.3, настоящий косинус), `fact_margin` (0.12, 0 = выкл.),
`dedup_similarity` ∈ [0.85, 1] (0.92), `search_limit` ∈ [1, 50]. Калибровка: `/facts probe <запрос>`.

План и статус — в [rag-facts.md](rag-facts.md).

## Сессии

- Идентификатор `{user_id}-{timestamp_ms}-{salt}`.
- `init` идемпотентен и защищён блокировками (`init_lock`, `meta_lock`, `OnceCell`-слот пользователя, повтор при вытеснении состояния).
- `finish` сбрасывает БД и освобождает память; для `uid = 0` стирает сессию с диска.
- `clone` копирует пары и локальные правила и регистрирует новую сессию.
- `clear` удаляет пары и обнуляет метаданные (правила остаются).
