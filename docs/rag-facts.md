# Оптимизация RAG-памяти (facts)

Цель: находить нужные факты с первого раза, не тратя LLM-вызовы на перевод и «улучшение» текста.

> Эффект на качество не измерялся (нет доступа к вашим данным и модели): после обновления выполните калибровку из [cistern-search.md](cistern-search.md#калибровка-за-пять-минут).
> Гипотезы ниже основаны на коде ядра; найденная позже причина п. 7 — метрика L2 в `cistern`.

## 1. Диагноз

| # | Что в коде | Чем вредит |
|---|---|---|
| 1 | **Перевод запроса** (`search_facts`): `whatlang` + LLM `translate_to_english` | +1 LLM-вызов и задержка на каждый не-английский запрос. `whatlang` ненадёжен на коротких строках; при `None` (`unwrap_or(false)`) переводится даже английский |
| 2 | **Перевод и расширение при записи** (`normalize_fact_text`) | Ещё один LLM-вызов; эмбеддится не факт, а его «раздутая» английская версия с шаблонными оборотами («The user…»), которая сильно отличается от короткого запроса |
| 3 | Промпт просит 3–7 keywords, но схема `NormalizedFact` возвращает только `search_text` | Ключевые слова генерируются и выбрасываются |
| 4 | Дедупликация удаляет **всех** соседей выше 0.8 | Общий шаблонный хвост завышает схожесть: «У пользователя кошка Том» может стереть «У пользователя собака Рекс». Тихая потеря данных |
| 5 | Авто-RAG ищет по **целому сообщению** (а на итерациях > 0 — по тексту control prompt) | Вектор размыт, при рекурсии ищется мусор |
| 6 | Только векторный поиск, хотя описание `search_fact` обещает «semantic and keyword» | Имена, версии, модели железа (`RTX 4070`, `Arduino Pro Micro`) эмбеддинги размазывают |
| 7 | Абсолютный порог `fact_similarity = 0.2`; в коде он называется `dist` | Неясно, это схожесть или расстояние. Если схожесть, порог 0.2 пропускает почти всё (шум в промпте), если расстояние — слишком строг. Оба варианта дают «плохо ищет» |
| 8 | Промпт: «Always call search_fact…» при включённом авто-RAG | Лишний круг: tool-call → control-итерация → ещё один LLM-вызов |
| 9 | Нет метрик качества | Пороги подбираются «на глаз» |

## 2. Принцип

Переводить не нужно: модель embeddings многоязычная, а **кросс-язычность лучше всего решается одним
пространством без посредников**. LLM для улучшения запроса и факта уже есть: это сам оркестратор, он и так
генерирует вызов tool. Пусть он сразу отдаёт то, что нужно индексу.

## 3. Запись: ноль дополнительных вызовов

Заменить `normalize_fact_text` полями, которые модель заполняет в момент `remember_fact`:

```rust
#[derive(Deserialize, Schema)]
pub struct RememberFact {
    /// Self-contained statement about the user, 3rd person, ≤200 chars, in the user's language.
    /// Name the subject explicitly (no pronouns); keep names, numbers, versions.
    pub text: String,
    /// 2–5 short keywords: entities and topics (English or original).
    #[serde(default)]
    pub tags: Vec<String>,
    /// ID of an existing fact that this one updates or replaces.
    #[serde(default)]
    pub replaces: Option<u64>,
}
```

- В эмбеддинг идёт `text + "\n" + tags.join(", ")` (`Search::Document`). Язык исходный.
- `UserFact.search_text` заменяется на `tags` (`#[serde(default)]` для старых записей). Старые факты переиндексирует команда `osy facts reindex`.
- Если `tags` не пришли, это не ошибка: работает чистый `text`.
- Расчёт: «Запомни…» = 1 LLM-вызов (вместо 3 сейчас, вместе с п. «silent ops» из [improvements.md](improvements.md)).

## 4. Чтение: строить запрос детерминированно

**Убрать** перевод. Embedding запроса — как есть, `Search::Query`.

**Авто-RAG**: функция `build_fact_query(msg)` без LLM:

1. Только последнее сообщение пользователя. На итерациях > 0 повторно не искать: переиспользовать факты итерации 0 (кэш в состоянии запроса).
2. `strip_markdown` (уже есть) + удаление блоков кода + срез до ~300 символов.
3. Шлюз: не искать, если меньше 2 слов или это реплика-«пустышка» («ок», «да», «спасибо»). Стоп-лист по языкам — десяток слов.
4. Длинное сообщение: разбить на предложения, взять до 3 самых «содержательных» (длиннее N символов), эмбеддить пачкой, объединить результаты по максимуму оценки.

**Явный `search_fact`:**

```rust
pub struct SearchFact {
    /// 1–3 short queries (2–6 words each), in the user's language. Different angles of the same need.
    pub queries: Vec<String>,
    #[serde(default)] pub limit: Option<usize>,
}
```

Один вызов закрывает несколько формулировок и не требует лишних итераций. Убрать из описания требование «query in English».

**Промпт оркестратора**: заменить «Always call `search_fact`…» на
«Relevant facts are preloaded below. Call `search_fact` only if a specific detail is missing».

## 5. Гибридный поиск

Факты короткие и их немного (сотни, максимум тысячи), поэтому лексический индекс живёт в памяти пользователя:

- **BM25 по символьным 3-граммам** от `text + tags`: работает с русской морфологией без стеммера, ловит имена, числа, версии.
- Загружается при `UserState::connect` (один `read_all`), обновляется в `save_fact` / `remove_fact`.
- Слияние: векторный top-20 + лексический top-20 → **RRF** (`score = Σ 1/(60 + rank)`) → top-N.

Если `cistern` умеет FTS в LanceDB, можно взять его, но in-memory вариант проще и не зависит от версии.

## 6. Отбор результатов

- Вместо одного абсолютного порога: **относительный** (оставить результаты не хуже `0.8 × top`) + мягкий абсолютный минимум после калибровки.
- Лимит по **бюджету символов** (~600), а не только по числу: 10 длинных фактов могут стоить больше, чем 3 коротких.
- В промпте — **короткие ID** (`#1…#n` на запрос) вместо 19-значных `u64`: на ~10 токенов дешевле на каждый факт и правило при каждом вызове. Сопоставление `#n → u64` хранится в состоянии запроса.

## 7. Дедупликация без потерь

Ядро никогда не удаляет факты молча.

1. Точное совпадение текста (без регистра) → no-op.
2. Явный `replaces: Some(id)` → удалить старый, записать новый.
3. Высокая схожесть с существующим (≥ ~0.92 после калибровки) и нет `replaces` → ядро **ничего не пишет** и возвращает модели:
   `Similar fact exists: #3 "…". Call remember_fact with replaces=3 to update, or ignore.`
   Лишний круг возникает только при конфликте, зато данные не теряются.

## 8. Оценочный стенд (делать первым)

Без измерения настройка порогов бессмысленна.

- `osy facts eval cases.jsonl`: строки `{"query": "...", "expect": ["подстрока факта"]}`, 30–50 пар из реальных данных: русские, английские, смешанные запросы, запросы по именам.
- Метрики: `recall@k`, `MRR`, среднее число внедрённых фактов, доля запросов с шумом (внедрено, но не ожидалось).
- Режим `--debug`: печатать **сырые оценки** (чтобы выяснить смысл `fact_similarity`: схожесть это или расстояние).
- Прогонять варианты: `translate on/off`, `normalize on/off`, `hybrid on/off`, разные пороги. Оставлять тот, что выигрывает по recall при меньшем шуме.

## 9. Дополнительно

- LRU-кэш эмбеддингов запросов (256 записей): повторы запросов в сессии бесплатны.
- Батч-эмбеддинг при `reindex`.
- Эксперимент (A/B на стенде, не по умолчанию): шаблон запроса вида `"User fact: {q}"`. Для некоторых моделей с режимами query/document он помогает, для других вредит.

## 10. План внедрения

| Шаг | Что | Риск |
|---|---|---|
| 1 | Стенд + отладочный вывод оценок | нет |
| 2 | Убрать перевод запроса, `build_fact_query`, не искать на control-итерациях | низкий |
| 3 | `tags` и `replaces` в `remember_fact`, убрать `normalize_fact_text`, `facts reindex` | миграция данных |
| 4 | Безопасная дедупликация | низкий |
| 5 | Гибрид (BM25 3-граммы + RRF) | средний |
| 6 | Относительный порог, бюджет символов, короткие ID | низкий |

Ожидаемый эффект по стоимости: чтение не-английского запроса −1 LLM-вызов, запись факта −1 LLM-вызов, меньше лишних итераций из-за `search_fact`.
Эффект по качеству должен подтвердиться стендом.
