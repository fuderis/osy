## P0. Корректность

### P0-1. Ошибки tools — в результат tool

`js_eval` в оркестраторе и любой `Err` воркера в skill завершают запрос; ошибки агента (`Event::Error`) в результат не попадают.
Модель не может исправить свой вызов. Правка в [self-healing.md](self-healing.md#конкретные-правки) занимает несколько строк и оживляет весь механизм.

### P0-2. Повтор не должен повторять выполненное

При ошибке одной из параллельных задач `continue 'iteration_loop` планирует всё заново без результатов успешных задач.
Хранить `completed` и показывать модели «A: done, B: failed. Retry only B».

### P0-3. Авто-RAG на служебном тексте

В `handle_query` авто-RAG берёт `message.extract_texts()`. На итерациях > 0 это control prompt: ищутся факты по служебной фразе (лишний embedding и шум в промпте).
Решение: искать только при `iteration == 0` по `root_user_msg` и переиспользовать факты.

### P0-4. Деструктивная дедупликация

`save_fact` удаляет всех соседей выше `dedup_similarity`, не глядя на смысл. Подробности и решение — [rag-facts.md, п. 7](rag-facts.md#7-дедупликация-без-потерь).

### P0-5. Накопление system-сообщений (проверить)

`messages`, который передаётся в рекурсивный `handle_query`, уже содержит system-сообщения (карта диалога, блок rules/facts/assist-prompt), а на следующей итерации
они **добавляются снова** к `raw_messages`. Кроме того, при `iteration == 0` сообщение пользователя дописывается в контекст ещё раз (`guard.add_message(message.clone())`),
хотя оно уже входит в `builder`. Если `anylm` не фильтрует дубли по `Visibility::Internal`, то промпт растёт с каждой итерацией ровно там, где проект должен экономить.

Проверка: поднять `max_iterations`, сделать запрос с `use_skill` и посмотреть `CONTEXT MESSAGES` (дамп уже есть, см. P0-6) на итерациях 1–2.
Исправление: хранить в рекурсии только «хвост» (сообщения текущего хода), а system-блоки собирать заново на каждой итерации из источников.

### P0-6. Дамп контекста в `warn!`

`warn!("CONTEXT MESSAGES: {:#?}", …)` пишет в лог rules, facts и историю при каждой итерации. Убрать или перенести за `RUST_LOG=trace` / флаг конфига.
Аналогично `Calling x.y.z tool: {json}` уходит в лог и клиенту как `Thinking`: если в аргументах секрет, он будет виден.

## T. Токены

### T-1. Silent-операции

`remember_fact`, `notes` (и `search_fact`, если авто-RAG уже дал результат) не требуют control-итерации, если модель уже написала ответ.
Сейчас любой вызов этих tools запускает ещё один полный LLM-вызов. Решение: поле `silent` у результата; `had_actions` считается только по несилентным операциям, либо при пустом тексте.
Экономия: 1 из 3 вызовов на «запомни».

### T-2. Результат skill — напрямую пользователю

Сейчас для одного действия: планирование (1) → skill (≥2) → control (1) = ≥ 4 вызова, причём skill уже сформулировал ответ,
а оркестратор пересказывает его целиком с полным контекстом.

Предложение: параметр `use_skill{ finalize: "direct" | "llm" }` (по умолчанию `direct`, если задача одна и оркестратор не написал текст).
При `direct` текст skill стримится как `Answer`, control-итерации нет. `llm` — когда ответ нужно скомбинировать или объяснить.
Дополнительно: skill возвращает **сжатый результат**, а не вежливое сообщение (T-6).

### T-3. Порядок контекста под prompt caching

Сейчас статичная часть (assist prompt, список skills) стоит в последнем system-сообщении после истории, а в начале лежит карта диалога, которая меняется каждый ход.
Для провайдера с prompt caching кэшируемый префикс почти пустой. Системный блок содержит время с секундами.

Порядок «стабильное → изменчивое»:

```
[system]  assist prompt + список skills + rules        ← меняется редко
[system]  dialog map                                   ← меняется раз в ход
[history] последняя пара (+ шаги хода)
[system]  время (с точностью до минуты) + notes + facts ← меняется часто
[user]
```

Если провайдер не кэширует префиксы, ничего не теряется. Размер: S.

### T-4. Карта диалога

- **Кэш:** держать готовую карту в `Session` и обновлять инкрементально в `write_messages` (сейчас — полное чтение всех пар из Sled на каждой итерации).
- **Лимит:** последние N ходов (например, 20) полностью, более старые — сжато или в виде резюме.
- **Скользящее резюме:** в конфиге уже есть `compress_prompt` и `preserve_messages`, но код их не использует. Реализовать: при превышении лимита свернуть старые ходы в 5–10 пунктов (фоновый вызов), хранить в `Key::Summary`.
- Для длинных ответов ассистента брать начало и конец (вывод чаще в конце).

### T-5. Короткие ID

В промптах правила и факты помечены `[ID: 17321…]` (u64, 19 цифр, токенизируется плохо). Использовать `#1…#n` на запрос с отображением в реальный ID на стороне ядра.
Размер: S, эффект на каждый запрос.

### T-6. Лаконичный skill-промпт

`SKILL_PROMPT` почти дословно повторяет `ASSISTANT_PROMPT` (персона, «subtle humor», «end with a clarifying question»).
Для исполнителя это лишние входные и выходные токены, а потом оркестратор всё равно переписывает. Выделить общий блок персоны и дать skill-роли строгий формат:
«Return only the result: facts, values, status. No greetings, no questions. ≤ N words».

### T-7. Fact-tools у skills — по запросу

Каждому skill добавляются схемы `remember_fact` и `search_fact`; skills редко ими пользуются, а схемы стоят токенов на каждом шаге. Включать флагом в `#[skill(facts = true)]`.
Это ещё и ближе к заявленной изоляции.

### T-8. Кэш tools агента

`handle_skill` на каждом вызове делает `POST /skills/{skill}/tools` по UDS. Схемы статичны до перезапуска агента: кэшировать в `Manager` при регистрации и сбрасывать в `refresh`.

### T-9. RAG

См. [rag-facts.md](rag-facts.md): убрать перевод, перенести «нормализацию» в аргументы `remember_fact`, гибридный поиск, безопасная дедупликация, стенд для оценки.

### T-10. Учёт токенов

Проект про экономию токенов, но самих токенов он не считает. Добавить `Event::Usage { prompt, completion, cached }` из ответов провайдера, суммировать на запрос, показывать в футере чата и писать в `osy trace`.
Дополнительно: `max_tokens_per_turn` в `[execution]`, чтобы «жёсткий потолок» стал реальным, а не только лимитом итераций.

### E-2. Self-healing v2
См. [self-healing.md](self-healing.md): ошибка как наблюдение, бюджеты, детектор циклов, частичный retry, backoff.

### E-3. Конфиг

- Разделить `max_iterations` на `orchestrator_max_iterations` и `skill_max_iterations`.
- Удалить или реализовать `preserve_messages` и `compress_prompt` (сейчас мёртвый код).
- `runtime.instruction_limit` на деле выставляет лимит итераций циклов Boa (`set_loop_iteration_limit`): назвать честно и добавить лимит рекурсии и общего времени.
- Валидация конфига при старте и сообщение вместо молчаливого дефолта.
- Выбор модели per-role: оркестратор, skill, служебные вызовы (если они останутся) — разные модели и цены.

### E-4. Тесты

В репозитории нет тестов ядра (только заглушка в шаблоне агента). Самое ценное — **сценарные тесты с mock-LLM**: подменяемый `Completions`, который отдаёт заранее заданные стримы
(текст, tool call, ошибка, пустой ответ). Покрыть: retry при ошибке стрима, JS-ошибка, падение одного из двух параллельных skills, лимит итераций, отключение клиента.
Плюс юнит-тесты `strip_markdown`, `SessionId::from_str`, `build_fact_query`, дедупликации.

### E-5. Безопасность

- `Dialog::Script` исполняется CLI сразу. Ввести политику: `Script` без предшествующего `Confirm` отклоняется клиентом, либо `Script` содержит флаг `needs_confirm` по умолчанию `true`.
- Проверить, что сервер на 7878 слушает только `127.0.0.1` (в коде CLI используется `127.0.0.1`, а привязка сервера находится в `pearce`). Иначе любой в сети может звать `/sessions/*/query`.
- Секреты: `Dialog::Secret` не логировать; фильтровать аргументы tools в `Thinking` и логах.
- Windows: `tokio::net::UnixStream` в `manager/agent.rs` доступен только на Unix, а README обещает Named Pipes. Либо `cfg`-ветка, либо убрать Windows из заявленной поддержки.

### E-6. Документация для авторов агентов

Шаблон `crates/agent` содержит один `hello`. Добавить примеры: tool с `Dialog::Confirm`, tool со стримом `Thinking`, skill с собственным `prompt`, работа с `current_path`. README шаблона не заполнен (`...` в описании).
