# Поиск и индексация в cistern

Описание `ContextTable` после переработки (`table.rs` + новый `lexical.rs`).

## Что было не так

| Проблема | Следствие |
|---|---|
| `nearest_to` без `distance_type`: LanceDB по умолчанию считает **L2**, а порог — `1 - coef` как для косинуса | Порог зависел от длины векторов. Для нормированных векторов `fact_similarity = 0.2` на деле означал косинус ≥ 0.6 (слишком строго), для ненормированных не проходило ничего. Дедупликация при `0.8` на деле удаляла факты с косинусом ≈ 0.6 |
| Лимит применялся до фильтра, результат без оценки | Нельзя отсечь «хвост» и откалибровать порог |
| Один путь поиска: только векторы | Имена и версии (`RTX 4070`, `Neovim`) размазываются в эмбеддинге |
| Чтение и вектора, и данных | Лишний трафик (особенно в `read_all`) |
| Каждый `write` = отдельный файл данных и версия; сжатия нет | Чтение замедляется со временем |
| `clear` оставлял схему; смена модели эмбеддингов (другая размерность) ломала запись | Только ручное пересоздание |
| `index(partitions, subvectors)` на любой таблице, ошибки обучения глушились, метрика индекса L2 | PQ на сотне векторов бессмыслен, `num_sub_vectors` мог не делить размерность |

## Алгоритм `search`

```
вектор запроса ──► [канал 1] косинусная близость (точный перебор, либо ANN при наличии индекса)
                      │  кандидаты: max(4·limit, 20), sim = 1 − distance
                      │  отбор: sim ≥ min_similarity  И  sim ≥ best − margin
текст запроса ───► [канал 2] лексический поиск по словам (lexical.rs), только если задан text
                      │  попадания допускаются независимо от косинуса
                      ▼
            слияние рангов (RRF, k = 60) ─► top-limit ─► ScoredRecord{ score, similarity, lexical }
```

- **Метрика явно `Cosine`**, `similarity = 1 − _distance`. Порог не зависит от длины вектора (регрессионный тест `similarity_is_cosine_and_scale_invariant`).
- **`margin`** отрезает хвост: если лучший хит 0.82, а остальные 0.55–0.60, это шум, даже если пол (`min_similarity`) ниже.
  Лексические попадания margin не режет.
- **RRF** устойчив к разным шкалам каналов; `score` — слитый ранг, нормированный в 0..1 (1 = первый в обоих каналах).
- Ошибка лексического канала не ломает векторный поиск.
- `read(vector, limit, coef)` оставлен для совместимости: вектор + порог, без слияния.

## Лексический канал (`lexical.rs`)

Находит редкие точные слова без индекса и стеммера:

1. Нормализация: нижний регистр, `ё → е`, слова из букв и цифр.
2. Совпадение слов: равны, либо общий префикс ≥ 3 символов и ≥ 60 % длинного слова (`кота ~ кот`, `использую ~ использует`;
   `пользователь ≁ пользуется`). Слова с цифрами совпадают только точно.
3. Только **специфичные** слова запроса: найденные не более чем в 40 % документов (`пользователь` в каждом факте сигнала не несёт);
   плюс короткий список стоп-слов (RU/EN), слова из 1–2 букв отбрасываются.
4. Оценка: idf-взвешенная доля совпавших специфичных слов, `(0, 1]`.

Проверено на прототипе: «какая у меня видеокарта RTX» → только факт про RTX; «погода завтра» → ничего; «как зовут моего кота» → факт про кота.
Сканирование без состояния (нет индекса, который нужно синхронизировать), читаются только колонки `id` и `data`, лимит — 20 000 строк
(на больших таблицах канал отключается). Кросс-язычные совпадения (`кофе` ~ `coffee`) — задача векторного канала.

## Индексация и обслуживание

| Механизм | Поведение |
|---|---|
| **Без индекса при < 4096 строк** | Точный перебор: быстрее и точнее ANN, IVF-PQ на малом числе векторов не обучается |
| `ensure_index()` | От 4096 строк строит IVF-PQ (косинус): `sqrt(rows)` партиций (2..1024), число под-векторов — наибольший делитель размерности, дающий ≥ 8 измерений на под-вектор. Существующий индекс не трогает |
| Поиск при наличии индекса | `refine_factor = 5` возвращает точность, потерянную квантованием |
| `optimize()` | Сжатие мелких файлов, чистка старых версий, доиндексация новых строк |
| Автосжатие | Без состояния: раз в 16 версий таблицы и только на таблицах ≤ 200 000 строк (`write`, `write_batch`, `remove`) |
| `replace_all(items)` | Атомарная замена всего содержимого (`Overwrite`): переиндексация после смены модели, размерность может измениться |
| Проверка размерности | Запись вектора другой размерности в непустую таблицу — понятная ошибка; в пустую — таблица пересоздаётся |

## Подключение

`mod lexical;` и `pub use table::{ContextTable, ScoredRecord, SearchOptions};` в `context/mod.rs` (см. `MOD_PATCH.md`).

## Что в Osy

- `UserState::search_facts`: гибридный поиск, пол `fact_similarity` (теперь настоящий косинус, 0.3), `fact_margin` (0.12), `hybrid_search`.
- `UserState::probe_facts` и команда чата **`/facts probe <запрос>`**: топ-10 без порогов, с `sim` и `lex`. Так калибруется пол под вашу модель эмбеддингов.
- `UserState::reindex_facts` и **`/facts reindex`**: пересчёт эмбеддингов по исходному тексту (старые факты построены по английскому тексту от LLM).
  Ничего не пишется, пока не готовы все эмбеддинги; затем атомарная замена.

### Калибровка за пять минут

1. `/facts reindex`.
2. `/facts probe` с 3–5 запросами, на которые факт точно есть, и 3–5 запросами «ни о чём».
3. Пол `fact_similarity` поставьте между `sim` лучших нерелевантных хитов и `sim` релевантных. `fact_margin` оставьте 0.1–0.15, если релевантные хиты идут плотной группой.
4. Если `sim` релевантных и мусора почти не различаются, модель эмбеддингов слабо подходит для коротких фактов (тогда выручает лексический канал).
